# Taste
- Communicates in Spanish and expects responses in Spanish. Confidence: 0.7
- Expects Laravel-style separation between framework/infrastructure code and app code: the `app/` tree is exclusively for the user's own domain code, so framework-provided/infrastructure code must live in a dedicated root-level `framework/` directory with its own namespace, not tucked inside `app/` (even as something like `app/Framework`). Treats infrastructure classes sitting in app-facing folders as misplaced. Confidence: 0.85
- Prefers the lowest-friction fix that reuses an existing layer over introducing new top-level namespaces/packages: when given options (move to existing `app/Support`, new `App\Framework` dir, real Composer package, drop the model), chooses the minimal one — but abandons minimalism once that layer degrades into a catch-all. Confidence: 0.55
- Rejects catch-all/dumping-ground folders: a directory that mixes framework infra with helpers, models, plain functions and reusable classes "sin distinguir" is called out as a mess. Expects structure to make each piece's role/component obvious (organize by component, not by vague "support" role), and that the intent is documented so helpers never get mixed back in. Confidence: 0.75
- Expects a convention established in one area to be propagated to every analogous layer (middleware, controllers, models, views, migrations, seeds, tests), and asks the assistant to proactively spot and propose such consistency improvements instead of only doing the literal request. Confidence: 0.65
- Wants conventions codified in written docs ("intended usage" / recommendations / development conventions) so new modules follow the established pattern instead of ad-hoc code; cares about keeping the codebase orderly as it scales. Expects such docs to read like official framework documentation (Laravel-style): teaching the stack's fundamentals and correct usage, not just a one-off task note. Confidence: 0.75
- Prefers domain-specific, distinctive names over generic umbrella names for directories and identifiers (e.g. `scaffolds/tasks` rather than `scaffolds/demo`), so that multiple sibling instances of the same kind can coexist without renaming later. Confidence: 0.6
- Expects scaffolding install/uninstall (or any create/remove) commands to be genuinely symmetric and residue-free across every layer — files, routes, views, tests, DB tables and migration log entries — and to leave the project in the same state as a fresh clone; wants this proven with real end-to-end runs, not just described. Treats leftover artifacts as a bug to hunt down. Confidence: 0.6
- Validates significant work by delegating independent reviews to multiple agents running different models, then expects the assistant to synthesize their outputs itself — separating genuine findings from noise and ordering what to address by severity/priority — instead of just relaying raw reviews. Confidence: 0.6
- Before committing/pushing, expects the assistant to prove the CI will pass (run the full local gate and the workflow's steps, ideally in a clean checkout sandbox) so GitHub Actions reports green instead of surfacing failures after the push. Confidence: 0.55
- Expects visual consistency across similar UI elements (e.g. icon sizes in navigation vs. logout must match); treats mismatched sizing as a defect to be fixed. Confidence: 0.55
